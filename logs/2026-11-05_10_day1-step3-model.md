## 2. The headline lesson: the FPR doubled on the future

We picked T_high so that **exactly** 60 of 60,000 val benign files score above it. On test the same threshold lets through **126**.

**Is it noise?** If the true FPR were still 0.1%, false positives on test would be Binomial(60000, 0.001) with mean 60 and σ ≈ 7.7. 126 is about 8.5σ out. `binom.sf(125, 60000, 0.001)` = **7.5e-14**, so it's not noise. The benign population changed between late November and early December 2024. This is **concept drift**, and specifically **drift in the benign tail**: a few new benign families (new software versions, new packers, installers) look like malware to a model that never saw them.

**Ranking drift vs. threshold drift.** The "oracle" row separates two effects:
- **Ranking quality** fell a little: at a correctly placed threshold, TPR at 0.1% FPR drops 93.6% → 90.3%, and pAUC 0.970 → 0.958.
- **Calibration / threshold placement** moved: the 0.1% threshold on test would be 0.999992, not 0.999917. The scores of the top benign files rose.

The two effects compound. On the *operating point* (fixed threshold) the FPR doubled, while the summary number ROC-AUC barely moved (0.9989 → 0.9982). **ROC-AUC averages over all FPRs, and almost all of that area is at FPRs we'd never run at.** That's why we track pAUC and FPR at the threshold, as the guide's KPI says.

Note also TPR @ 0.01% *rose* on test (71 → 78%). The ROC curve didn't shrink uniformly; it changed shape. One number never tells the whole story.

### Why we do NOT "fix" this by re-tuning on test
It's tempting: set T_high = 0.999992 and the test FPR is 0.1% again. But then test is just a second val set, and we'd have no honest estimate of next month. The real future (week 13+) will drift again. `axi.model test` writes `test_report.json` and **refuses to run again** without `--force`, to make this discipline mechanical.

What a real EDR does instead (each one validated on **val**, never on test):
1. **Safety margin:** target e.g. FPR 0.05% on val, expecting ~2× inflation. You can measure the inflation honestly inside val: pick on week 9, measure on week 10.
2. **Retrain often, on the most recent data.** Drift is a function of the time gap. Before production, retrain on weeks 1–10 (train+val) with the iteration count frozen, and keep the val-picked thresholds or re-derive them on a fresh holdout.
3. **Allowlisting / reputation:** signed binaries from known publishers and known-good hashes skip the ML verdict. That kills most of the benign tail cheaply. Our Day-2 sandbox zone is a softer version of this.
4. **More data:** the full Win32 train set (23.7 GB) covers more benign software variety. The memmap pipeline handles it with a config change (log 04).

## 3. What `axi/model.py` does, and why

### 3.1 Data
- **Train:** `lgb.Dataset("data/vectors/train.lgb.bin")` loads in **3.5 s**, compared with 134 s re-binning from the memmaps (log 09 §5.4). The categorical feature list is stored inside the binary.
- **Val:** dense 120k × 2568 float32 (1.2 GB), built with `reference=train_ds`, so it's binned with the *train* bin boundaries. LightGBM accepts float32 numpy arrays directly here (unlike the `Sequence` path).

### 3.2 Hyperparameters (`config.LGBM_PARAMS`)
| Param | Value | Why |
|---|---|---|
| `learning_rate` | 0.05 | Upstream grid uses {0.005, 0.05}. 0.005 would need ~10× the trees, 4+ hours here. |
| `num_leaves` | 512 | Bottom of upstream's grid {512, 1024, 2048}. Bigger trees fit faster but are slower to predict and overfit drift more. |
| `min_data_in_leaf` | 50 | A leaf must cover ≥ 50 samples, which damps memorizing single files |
| `feature_fraction` | 0.5 | Each tree sees a random half of the columns: decorrelates trees (random-forest idea inside boosting) and ~halves histogram work |
| `bagging_fraction`/`freq` | 0.8 / 1 | Each iteration uses a random 80% of rows: stochastic gradient boosting |
| `num_threads` | 8 | Physical cores. Histogram building is memory-bandwidth bound, so the 8 extra hyper-threads add little and make the PC unusable. |
| `metric` | `"None"` + custom `feval` | See 3.3 |

No hyperparameter search was run. Upstream's grid (`thrember.model.optimize_model`) is 108 configurations × 3 time-series folds, days of CPU on this machine. With a 2-day budget, sensible defaults plus early stopping is the right trade. If you want a search later: tune on val with **pAUC**, a handful of configs, `learning_rate` 0.1 for speed.

### 3.3 Early stopping on partial AUC, not logloss
- Boosting adds trees forever. Early stopping keeps the iteration with the best val score and stops after 200 non-improving rounds (patience).
- **Which score matters?** Default would be logloss (average over all samples). We operate at FPR ≈ 0.1%, so the only part of the ROC that matters is the far-left sliver. `_pauc_feval` computes sklearn `roc_auc_score(max_fpr=0.005)` each iteration: an O(n log n) sort of 120k scores, ~30 ms, negligible versus ~0.7 s per tree.
- `max_fpr` returns the **McClish-standardized** partial AUC: the raw area under the ROC for FPR ∈ [0, 0.005] rescaled so 0.5 = random and 1.0 = perfect. That's why the value (0.97) isn't tiny, even though the raw area is ≤ 0.005.
- Curve: 0.942 @50 → 0.964 @200 → 0.968 @500 → 0.9695 @1000 → **0.970003 @2063** (best) → stopped at 2263. After ~1000 trees the gains are ~1e-4 per 100 trees, which is under what you can resolve with 60k benign samples. It's a plateau, not overfitting. A patience of 200 is generous; we pay ~200 extra trees of time (~2.5 min) for robustness against noisy plateaus.
- ⚠️ Early stopping *is* a decision made on val, which makes val slightly optimistic, because we picked the best of 2263 checkpoints. Another reason test is the number to believe.

### 3.4 Threshold selection: `threshold_for_fpr`
Want the smallest t with FPR(score ≥ t) ≤ f. Sort benign scores descending: b[0] ≥ b[1] ≥ …; at most k = ⌊f · n_benign⌋ of them may be ≥ t. Choose **t = nextafter(b[k], +∞)**: the smallest float strictly greater than the (k+1)-th largest. Then b[k], and everything tied with it, falls below t.
- Correctness under ties was unit-checked: 10,000 benign all scoring 0.5 gives t = 0.5000000000000001, FPR 0 (not 100%).
- With k = 60 on val, the threshold rests on the 61st-highest benign score, an order statistic, so it's inherently noisy (±√60 ≈ ±8 files). That's another reason a fixed target FPR on future data isn't guaranteed.
- **Why the threshold is 0.999917, not 0.5 or the guide's 0.97:** on 50/50 data with a strong model, the benign tail starts very near 1. "0.5" means nothing operationally. The threshold is a *policy* (how many false alarms per day can the SOC absorb) translated into a score via the val benign distribution.
- **T_low** uses the same function at FPR 1%: the **sandbox budget**. 1% of benign files go to the (slow, expensive) sandbox. On val that zone also catches 2756 of the 3838 malware that T_high missed, which shows why a second stage is worth having.

### 3.5 Artifacts and integrity
- `axi_lgbm.txt` uses LightGBM's text format: portable across versions and platforms, readable, git-diffable. Saved with `num_iteration=best_iteration`, so the trees after 2063 are dropped.
- `axi_lgbm.json` carries the thresholds **with** the model they belong to, plus the model file's sha256. `Model()` refuses to load if the hash doesn't match. A threshold from one model applied to another is a silent, catastrophic bug: scores aren't comparable between models.
- `Model.verdict(score)` → `"pass" | "sandbox" | "quarantine"` is the interface the Day-2 daemon will use.

## 4. Precision reality check (base rate, log 09 §2)
Test-set precision at T_high is 55588 / (55588 + 126) = 99.77%. At a realistic 1000:1 benign:malware ratio, the same TPR/FPR gives 0.9265 / (0.9265 + 1000 × 0.0021) ≈ **31%**: two of every three quarantines would be benign files. That's why allowlisting (§2 item 3) and the sandbox zone matter more than another 0.001 of AUC.
