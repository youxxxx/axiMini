## 3. `docs/YARA_RULE_GENERATOR.md` (design only, not implemented)
A design document for the guide's ch. 15 stretch item. Written so a later session can pick it
up with every design decision already made. Sections:

1. **One-sentence spec** + an example rule, including the escape handling and the `uint16(0) ==
   0x5A4D` guard that stops the rule scanning non-PE content.
2. **Why it fits the project** — the vault + sidecar already keep everything the generator
   needs; this is just text output from existing artifacts.
3. **Interface** — Python function signature, CLI (Korean output, mirroring
   `axi.quarantine`'s style), and a read-only dashboard preview panel that respects the
   dashboard's write-free design from log 18.
4. **Indicator selection — the only interesting part.** Candidates ranked by specificity
   (-log P(appears in benign)) × stability (1 if invariant under recompile). A Bloom filter
   over benign val strings (120k files → 1 M bits ≈ 128 KB, k=4) lets the generator reject
   common candidates in O(1) at build time without re-reading the val set.
5. **Condition design.** `2 of (...)` with a `filesize < 2× sample` family filter, plus the PE
   magic check up front to short-circuit on non-PE content.
6. **Correctness traps**, covering the one the guideline already flags (string escape; the
   example `C:\Payloads\"; condition: true //` shows why it matters), non-printable bytes,
   rule-name collisions, and YARA version pinning.
7. **Testing** — round-trip via `yara-python`, property-test the escape function (round-trip
   through the parser), and a negative control that builds a rule from `notepad.exe` and
   asserts it doesn't match the benign val set.
8. **Deps to add** (`yara-python>=4.5`), with a `check_env.py` sanity call.
9. **Scope boundary** — explicitly NOT a retrain pipeline, NOT auto-deployment, NOT an
   unpacker.
10. **Rough effort**: ~6 h. Depends on Day 1 model (for the specificity ranking) and Day 2
    quarantine + dashboard (inputs + preview panel).

### Why write the design now instead of the code
- The user picked option 3 ("guide markdown file"), so the deliverable is a doc.
- A design doc at this moment captures the context (thresholds, vault layout, dashboard
  constraints) while it's fresh; a future implementer won't have to re-derive the Bloom-filter
  size or the escape trap.
- The real work in a YARA generator is choosing the indicators, not the output format. The
  Bloom-filter + specificity-score plan is the part worth writing down.
